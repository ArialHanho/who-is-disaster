# 코드 비서 고도화 계획

비서는 이번 변경으로 영향을 받는 코드와 수정할 순서를 브리핑에서 먼저 보여줍니다. Git 수집과 정적 의존성 검사는 연결한 브랜치, PR, 선택한 작업 폴더 전체를 다룹니다.

## 출발점

v0.3.3의 로컬 기록에서 문서 한 파일만 바뀐 점검 세 번이 각각 AI 검토 75묶음을 다시 요청했습니다. 74묶음을 재사용한 재시도는 3분 15초 걸렸습니다. 브리핑은 코드 문제 506건을 집계했지만 최근 80건을 가져온 뒤 필터를 적용해 37건만 보여줬습니다. 같은 코드 근거도 모델의 식별자가 달라지면 새 문제로 저장됩니다.

## 진행 순서

1. **브리핑 목록** — 저장소·상태·분류를 전체 결과에 적용한 다음 페이지를 나눕니다. 최근 분석에서 처음 발견된 문제를 먼저 보여주고, 알림이나 기록에서 문제를 열면 해당 페이지로 이동합니다.
2. **이슈 식별과 근거** — 실제 원문 위치와 문제를 일으키는 구현·호출부를 기준으로 같은 이슈를 이어갑니다. 기존 오탐·설계 유지 결정과 해결 이력을 읽을 수 있어야 합니다. 호출 관계를 확인하기 어려운 분석은 검토 후보로 표시합니다.
3. **검토 시간** — 전체 소스 검토의 캐시는 묶음과 관련 코드의 내용에 연결합니다. 새로 발견한 이슈를 먼저 저장해 브리핑에 표시하고, 기존 문제의 수정 여부는 관련 코드가 바뀐 항목부터 재확인합니다.
4. **분석 범위와 테스트** — 브랜치별로 분석 포함 여부를 저장합니다. 미커밋 포함을 켠 로컬 연결은 파일 저장 후 자동 점검 대상으로 잡습니다. 문제 카드에서 관련 GitHub 커밋의 Actions 실행 결과를 필요할 때 조회합니다. 가상 통합본에는 실제 실행 여부를 명시합니다.

## 완료 기준

- 한 저장소에 80건을 넘는 결과가 있어도 집계된 모든 문제를 탐색할 수 있습니다.
- 같은 근거의 문제는 모델 식별자가 바뀌어도 다시 알리지 않습니다. 관계없는 호출문은 확실한 문제의 근거가 되지 않습니다.
- 문서 한 건을 수정한 경우 관련 문맥이 같은 소스 묶음은 재사용됩니다. 기존 이슈의 재확인이 진행 중이어도 새 이슈를 열 수 있습니다.
- 커밋을 만들기 전에도 저장된 작업 파일의 변경을 감지합니다. 실제 커밋의 검사 성공·실패·기록 없음과 가상 통합본의 미실행 상태가 문제 상세에서 구분됩니다.
- 제외한 브랜치의 변경은 점검을 예약하지 않습니다. 새 브랜치 자동 포함 설정으로 이후에 생긴 브랜치를 따라갈 수 있습니다.

검토 대상의 Git 객체는 읽기 방식으로 수집합니다. 자동 점검의 변경 병합과 대기 정책을 적용하고, Actions 결과는 사용자가 조회할 때 가져옵니다. 첫 유효 결과까지 걸린 시간, 중복, 오탐, 놓친 결함을 실제 변경 사례로 비교합니다.

## 구현 검증

100건을 저장한 브리핑에서 예전 조회 한도 밖의 항목을 필터와 문제 링크로 열었습니다. 코드 파일 210개와 문서 한 개로 구성한 검토에서 문서 수정 후 코드 묶음을 재사용했고, 새 요청은 변경 비교와 수정된 문서에 각각 한 건이었습니다. 저장된 작업의 변경 감지와 수집 시점의 일치, 관련 커밋의 Actions 조회, 기존 설계 유지 판단의 보존도 검사했습니다.

다음 실제 사용 측정에서는 같은 저장소의 연속 푸시에서 첫 결과까지 걸리는 시간과 AI 요청 수를 기록합니다. 호출 관계를 정적으로 확인하기 어려운 경우에는 후보를 보여주고, 사용자가 확인한 오탐과 놓친 문제를 다음 개선 사례로 남깁니다.
